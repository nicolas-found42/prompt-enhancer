# Modern Python and web development tooling

Research date: 2026-09-24. Scope: the existing Python package and React/TypeScript/Vite app. Recommendations below are based on repository files and the linked first-party documentation; they are not a mandate to adopt every available rule.

## Current baseline

- [`pyproject.toml`](../../pyproject.toml) targets Python 3.11+, uses setuptools, declares FastAPI/Pydantic/Uvicorn as runtime dependencies, puts `httpx` and `pytest` in a published optional `dev` extra, and puts pre-commit, Ruff, and ty in uv's local `dev` dependency group. [`uv.lock`](../../uv.lock) currently resolves Ruff 0.16.8, ty 0.0.83, pytest 9.1.1, and pre-commit 4.6.2.
- [`.pre-commit-config.yaml`](../../.pre-commit-config.yaml) already invokes staged Ruff formatting and lint fixes, whole-repo Ruff and ty checks, pytest, a TypeScript/Vite build, and Playwright. [`web/package.json`](../../web/package.json) also has ESLint and Prettier. There is no `.python-version`, declared Node engine, or CI workflow in this checkout.
- [`web/package-lock.json`](../../web/package-lock.json) currently resolves Vite 8.3.0, TypeScript 6.0.3, React 19.3.0, `@vitejs/plugin-react` 6.1.1, and Playwright 1.63.0. `web/package.json` uses `latest` for its five main packages; the lockfile still gives exact installed versions when `npm ci` is used. npm documents `npm ci` as a clean, lockfile-based install that fails when package metadata and lock disagree. ([npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/))

## Python recommendations

1. **Keep uv as the sole Python environment and lockfile workflow.** `uv run` checks project metadata and syncs the environment before running a command; `uv sync --locked` and `uv lock --check` fail when the lock is stale instead of rewriting it. uv recommends committing `uv.lock`, while `uv sync` installs the `dev` group by default. Use `uv sync --locked` for repeatable setup and `uv run --locked` in verification commands. ([uv projects](https://docs.astral.sh/uv/guides/projects/), [uv locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/))
2. **Put test-only dependencies in `[dependency-groups].dev`.** uv distinguishes publishable extras from local development groups, and extras are not synced by default. Here `pytest` and `httpx` support the repository's tests, so moving them from `[project.optional-dependencies].dev` to the existing `dev` group makes `uv sync --locked` sufficient for all routine checks. Preserve an optional extra only if external consumers intentionally install it. ([uv dependency fields](https://docs.astral.sh/uv/concepts/projects/dependencies/), [uv sync defaults](https://docs.astral.sh/uv/concepts/projects/sync/))
3. **Use one Ruff configuration for formatting, imports, and lint.** Ruff's formatter does not sort imports; its documented sequence is `ruff check --select I --fix` followed by `ruff format`. Enable import sorting with `I` and consider a measured `E`, `F`, `UP`, `B`, `SIM`, or `RUF` selection after reviewing actual violations. Ruff warns that some rules conflict with formatting, so rule changes should be checked against its compatibility list and applied in a reviewed baseline pass. Target Python 3.11 consistently with `requires-python` (or explicitly with Ruff's `target-version`). ([Ruff formatter](https://docs.astral.sh/ruff/formatter/), [Ruff configuration](https://docs.astral.sh/ruff/configuration/))
4. **Use ty in the uv environment and check the intended scope.** ty reads the lower bound of `requires-python`, so the package's `>=3.11` is already a useful target. `uv run ty check` locates dependencies through the uv environment. Current `ty check src scripts` leaves tests out; adding tests is a deliberate scope expansion and should be paired with fixes for any newly reported diagnostics. ty supports project-level `[tool.ty]` configuration and rules, with source-specific suppressions for exceptional cases. ([ty type checking](https://docs.astral.sh/ty/type-checking/), [ty Python version](https://docs.astral.sh/ty/python-version/), [ty configuration](https://docs.astral.sh/ty/configuration/))
5. **Make local and CI checks invoke the same commands.** The existing pre-commit hooks can call uv's project-local tools; a CI job should run `uv sync --locked`, formatting in check mode, Ruff, ty, and pytest. The lock check guards against accidental dependency resolution during validation. Whether to run slow browser tests on every local commit is a workflow tradeoff; Playwright's first-party docs describe the browser installation step. ([uv locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/), [Playwright browsers](https://playwright.dev/docs/browsers))

## TypeScript, Vite, and React recommendations

1. **Declare and enforce a supported Node range.** Current Vite requires Node 20.19+ or 22.12+. The observed local Node is 26.9.0. Add a `package.json` `engines.node` range and a version hint such as `.nvmrc` so developers and CI use a supported runtime. Check the current Vite migration guide before any major-version upgrade; Vite 8 replaced Rollup/esbuild internals with Rolldown/Oxc and changed its default browser target. ([Vite getting started](https://vite.dev/guide/), [Vite 8 migration](https://vite.dev/guide/migration))
2. **Classify packages by use and replace floating `latest` specifiers.** React and React DOM are application runtime dependencies. Vite, its React plugin, and TypeScript are build/development tools and belong in `devDependencies`. npm defines those fields accordingly. Use bounded major ranges or explicit versions for deliberate upgrades, regenerate the lockfile, and use `npm ci` in repeatable setup. This recommendation is about reviewability; the existing lockfile already pins a concrete tree. ([npm dependency fields](https://docs.npmjs.com/specifying-dependencies-and-devdependencies-in-a-package-json-file/), [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/))
3. **Keep TypeScript type checking separate from Vite's transform.** Vite intentionally transpiles TypeScript without type checking and recommends `tsc --noEmit` beside production builds; the current `build` script already does this. A watch-mode `tsc --noEmit --watch` is optional for immediate dev feedback. TypeScript 6 has migration/deprecation changes, so adjust `tsconfig` deliberately, verifying each option against the 6.0 release notes rather than copying an older template wholesale. ([Vite TypeScript features](https://vite.dev/guide/features), [TypeScript 6.0 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html))
4. **Strengthen linting incrementally.** The current ESLint config uses basic typescript-eslint recommended rules and only two React Hooks rules. React's `recommended` preset covers additional correctness checks; enabling it may reveal existing findings. typescript-eslint's `recommendedTypeChecked` preset with `parserOptions.projectService: true` adds type-aware linting but costs more than syntax-only linting, so it suits a whole-project check after the fast staged checks. Keep Prettier for formatting and `tsc` for type checking. ([React Hooks ESLint plugin](https://react.dev/reference/eslint-plugin-react-hooks), [typescript-eslint typed linting](https://typescript-eslint.com/getting-started/typed-linting/))
5. **Make Playwright setup portable and explicit.** [`web/playwright.config.ts`](../../web/playwright.config.ts) launches the API through `../.venv/bin/python` and uses a shell variable assignment in the Vite command. Playwright supports `webServer` arrays with `command`, `cwd`, and `env`; those fields can start the API through uv and pass its target to Vite without shell-specific assignment syntax. Keep `baseURL` and server readiness URLs. Browser binaries still require Playwright's install command after npm installation. ([Playwright web server](https://playwright.dev/docs/test-webserver), [Playwright browsers](https://playwright.dev/docs/browsers))
6. **Keep the API proxy target server-side.** Vite's `loadEnv` loads the configured prefix by default; the current config passes an empty prefix to read `PROMPT_ENHANCER_API_TARGET` for the dev proxy. Vite exposes `VITE_` variables to client bundles and warns against placing secrets there. The proxy target should stay a development server setting rather than be exposed to browser code. ([Vite JavaScript API](https://vite.dev/guide/api-javascript), [Vite environment variables](https://vite.dev/guide/env-and-mode))

## Suggested verification sequence

```text
uv lock --check
uv sync --locked
npm --prefix web ci
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked ty check src scripts
uv run --locked pytest -q
npm --prefix web run lint
npm --prefix web run typecheck
npm --prefix web run build
npm --prefix web run test:e2e
```

The exact ty scope and Ruff rule set should match the implementation after baseline findings are repaired. Playwright also needs its browser binary installed; the existing test config starts both the fake API and Vite server. ([ty file selection](https://docs.astral.sh/ty/type-checking/), [Ruff formatter check mode](https://docs.astral.sh/ruff/formatter/), [Playwright browsers](https://playwright.dev/docs/browsers), [Playwright web server](https://playwright.dev/docs/test-webserver))

## CI references

The resulting workflow installs uv with its [official GitHub Action](https://docs.astral.sh/uv/guides/integration/github/), installs Node with [setup-node](https://github.com/actions/setup-node), and follows Playwright's [CI browser installation guidance](https://playwright.dev/docs/ci). Playwright recommends one worker on CI for stability. The default dev environment omits the optional CatBoost dependency, so the workflow runs its training-path test separately with `--extra training`.
