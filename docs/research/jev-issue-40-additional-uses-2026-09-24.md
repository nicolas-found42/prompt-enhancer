# Jev opportunities at the issue 40 boundary

Research date: 2026-09-24. Scope: [issue #40](https://github.com/nicolas-found42/prompt-enhancer/issues/40), especially a writer response that omits a Choice description. This note adds issue-specific findings to [the broader Jev capability survey](jev-capability-opportunities-2026-09-24.md); it does not repeat its taxonomy, grading-batch, or fidelity proposals.

## What Jev can do when a description is missing

**Jev cannot write the missing sentence.** Its API returns a Noul probability, a selected Choice option and distribution, or a Score and level distribution. TypeSafe explicitly says Jev 1.13 is not trained to generate text; for text generation it recommends a generative model. OpenRouter's first-party prompt-to-questions example likewise has Claude write the questions and Jev answer them. [TypeSafe API reference](https://docs.typesafe.ai/api) · [TypeSafe Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13) · [OpenRouter prompt-to-questions lab](https://openrouter.ai/labs/jev/compile)

**Jev can judge a proposed repair.** A Noul can answer a narrow yes/no question, a Choice can select among descriptions supplied in advance, and several questions can be evaluated against one state. TypeSafe's extraction cascade uses a generative model to propose text and Jev to verify its semantics. This supports a bounded repair loop: detect the missing field in code, ask the writer for the missing description, then have Jev audit the completed success test before it is accepted. This loop is a recommendation for this repository, not a TypeSafe-prescribed success-test workflow. [TypeSafe Noul](https://docs.typesafe.ai/primitives/noul) · [TypeSafe Choice](https://docs.typesafe.ai/primitives/choice) · [TypeSafe SDE cascade](https://docs.typesafe.ai/cookbooks/sde_cascade)

**A missing description does not automatically mean an invalid Jev request.** TypeSafe permits `null` for a Choice option that needs no extra detail and demonstrates it with self-explanatory tone labels. A Jev Noul could judge whether a label is sufficiently clear relative to its sibling options, after which code could send `null`; that is an inference from documented Noul and Choice behavior, not a documented repair feature. It would be an exception to the issue 40 decision to have the writer supply a short description for every generated option. Do not treat omission itself as evidence that `null` is appropriate. [TypeSafe API reference](https://docs.typesafe.ai/api) · [TypeSafe Choice](https://docs.typesafe.ai/primitives/choice) · [TypeSafe Noul](https://docs.typesafe.ai/primitives/noul)

## Issue 40-specific implementation opportunities

1. **Repair once, then audit with Jev.** The [compiler currently asks the writer for label strings only](../../src/prompt_enhancer/success_tests.py#L66-L74), parses those strings, and runs [one whole-test faithfulness Noul](../../src/prompt_enhancer/success_tests.py#L87-L146). Extend the writer's schema to require descriptions. Code should identify absent or blank descriptions; a bounded writer repair can fill them. Run the existing Jev faithfulness check on the *completed* test, including descriptions, before grading receives them. If repair still omits a required description, discard that test; the Round already has an [unverified outcome when no faithful tests remain](../../src/prompt_enhancer/rounds.py#L287-L314). The structural omission is exact JSON validation, which TypeSafe says to keep in code; the description's faithfulness is a semantic judgment suitable for Jev. [TypeSafe Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13) · [TypeSafe SDE cascade](https://docs.typesafe.ai/cookbooks/sde_cascade)

2. **Define the compiler-added `unknown` option.** If a Choice has at least two labels and lacks `unknown`, [the parser adds `unknown` itself](../../src/prompt_enhancer/success_tests.py#L189-L207). The writer therefore cannot have supplied a description for that added key under the present shape. Issue 40 should either require the writer to return `unknown` with a description, or give the code-added key a deliberate fixed description and include that completed test in Jev's audit. TypeSafe says an `other`/`none of the above` option is useful when listed choices may not cover the input, and says descriptions should separate options. This is a contract choice for this repo, not an automatic Jev capability. [TypeSafe Choice](https://docs.typesafe.ai/primitives/choice)

3. **Audit boundary quality, if evidence warrants an additional Jev question.** The current faithfulness Noul asks both whether the test matches the request and whether it avoids an invented requirement, but it does not directly ask whether Choice descriptions distinguish neighboring options. TypeSafe advises one judgment per Noul and says option descriptions should separate the options. A second Noul over `{prompt, proposed_test}` could ask whether each description defines a distinct answer boundary; a low value would trigger writer repair or test rejection. This is an untested design inference. It is more relevant to issue 40 than the broad question-wording optimization proposed in [issue #51](https://github.com/nicolas-found42/prompt-enhancer/issues/51). [Current faithfulness question](../../src/prompt_enhancer/success_tests.py#L97-L110) · [TypeSafe Noul](https://docs.typesafe.ai/primitives/noul) · [TypeSafe Choice](https://docs.typesafe.ai/primitives/choice)

4. **Make the state pointer explicit in structured batch instructions.** TypeSafe says question IDs are not shown to the model, while named fields inside structured instructions are. The current batch builder puts distinct request states under `state.items` and prefixes string instructions with `For state.items[...]`; issue 40's object/array handling should preserve an explicit `item` reference to the correct state path. This is within #40's pass-through change, and does not require a new Jev decision. [TypeSafe API reference](https://docs.typesafe.ai/api) · [Current batch builder](../../src/prompt_enhancer/jev.py#L104-L127)
